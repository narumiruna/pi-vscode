## Discovery and scope boundaries

- Read the official [VS Code 1.106.0 encoding definitions and canonical-name mapping](https://github.com/microsoft/vscode/blob/1.106.0/src/vs/workbench/services/textfile/common/encoding.ts) and current upstream definitions. The minimum version has 48 setting identifiers; current upstream adds `cp857` (49 total). Forty-one have Node `TextDecoder` counterparts; eight require the new aliases above. UTF/Windows/ISO normalization and already-recognized names remain unchanged.
- `cp437`, `cp852`, `cp1125`, `cp857`, `koi8ru`, `koi8t`, `cp865` and `cp850` lack a `TextDecoder` equivalent in the tested runtime. They remain fail-closed rather than being mapped to a similar codec. Adding an alternative codec library is outside this alias fix, not an unaddressed request to normalize an existing counterpart.
- Node and VS Code's iconv codec tables can differ despite accepting the same label. The first full matrix exposed Big5-HKSCS `9dee` decoding as a private-use character in Linux Node 26 but `㗎` in VS Code; Windows Node 24 decodes it as `㗎` too. ISO-8859-1 C1 controls similarly differ from WHATWG Windows-1252. Capture must reject when the actual decoder/editor strings differ, not reject a supported sequence on every runtime. Positive fixtures use independently encoded non-ASCII bytes that all tested implementations support; two additional agreement fixtures verify acceptance or rejection against the runtime's canonical decoder. No approximate codec or replacement decoding is introduced.
